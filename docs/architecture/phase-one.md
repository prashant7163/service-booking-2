# Service Booking Two phase-one architecture

## Architecture decision and contract snapshot

Authority: the approved [project specification](../discovery/project-specification.json), canonical approval-subject digest `227a4f029b576930530c4c5b388d2836963d9f7356913b5faf5f9dcc180c4c9b`, and Task 2 of the phase-one implementation plan. This document records the affected architecture decision; [the OpenAPI contract](openapi/service-booking-two.yaml) is the normative HTTP contract consumed by backend and frontend tasks. These are design records, not implementation verification or independent approval.

Use one React/TypeScript client, one Java 21 Spring Boot REST API, and one PostgreSQL database. Local Docker Compose serves the client and `/api` through one origin. Domain modules remain inside the API; no microservices, queues, caches, or real external integrations are introduced. Database migrations own constraints, application services own transactions, controllers validate and project records, and the client does not enforce inventory or authorization on behalf of the API.

| Module | Owned responsibilities and interfaces |
| --- | --- |
| `auth` | Single-role accounts, BCrypt passwords, digest-only verification/reset credentials, sessions; `registerCustomer(email,password,displayName) -> SessionView`, `registerProvider(...) -> VerificationPendingView`, `verifyProvider(token) -> SessionView`; authenticated `Actor(accountId,role,verified,suspended)`. |
| `catalog` | Fixed categories, one shop per provider, multilingual offerings, images, slot SKUs and search; `saveShop(actor,SaveShopCommand) -> ShopView`, `saveOffering(actor,SaveOfferingCommand) -> OfferingView`, `bulkSaveSlots(actor,offeringId,List<SaveSlotCommand>) -> List<SlotView>`, `publishOffering(actor,offeringId) -> OfferingView`, `search(SearchQuery,Optional<Actor>) -> Page<ServiceSummaryView>`, and unpublication cleanup. |
| `commerce` | One persistent cart per customer, reservations, attempts and marketplace orders; `changeQuantity(customer,slotId,quantity) -> CartView`, `removeLine(customer,cartLineId) -> CartView`, `checkout(customer,CheckoutCommand) -> CheckoutResult`. CheckoutCommand contains selectedCartLineIds, acceptedTotal, simulateOutcome and idempotencyKey. |
| `fulfillment` | Booking-scoped codes, delivery, expiry and order completion; `redeem(provider,bookingLineId,fourDigitCode) -> BookingLineView`, `expireDueLines(Instant now) -> ExpiryResult`. |
| `admin` | Only `suspendProvider(admin,providerId) -> SuspensionResult`, `releaseReservation(admin,cartLineId) -> ReleaseResult`, and `deliverExpired(admin,bookingLineId) -> BookingLineView`. |
| `simulation` | Replaceable VerificationPort for verification/reset, `PaymentPort.authorize(PaymentAttempt)`, and NotificationPort for confirmation, provider purchase, customer redemption and customer expiry. Deterministic adapters and test spies; normal logs contain event type/correlation ID only. No inbox route. |

## Identity, HTTP and disclosure boundaries

One normalized email identifies one account with exactly one of CUSTOMER, PROVIDER or ADMINISTRATOR. There is no public administrator registration. Customers must verify before reserving or checking out; providers must verify before publishing. Provider registration does not require administrator approval. Password reset and verification are simulated, single-use, and store credential digests only. SessionView exposes exactly accountId, role and verified.

Use a server-side session with `JSESSIONID`, HttpOnly, SameSite=Lax, Path=/, and Secure outside isolated local/e2e HTTP. Rotate the session on authentication and verification, invalidate on sign-out, and check provider suspension on every authenticated request as well as sign-in. The client bootstraps a CSRF token through `/api/auth/csrf` and submits `X-CSRF-TOKEN` for every browser mutation, including sign-in and registration. Tokens are bound to the current anonymous or authenticated session and refreshed when that session changes. No cross-origin credential access is enabled. The e2e control uses its separate test header and is not a browser product route.

Controllers enforce role before service work; repositories/services constrain every lookup or mutation to the actor's owner ID. Missing authentication is 401, wrong role, owner, verification state, suspension or CSRF is 403, unavailable/missing resources are 404, concurrent/domain-state conflicts are 409, and invalid input or an incorrect four-digit code is 422. Wrong-owner mutation returns a generic 403 without identifying the owner; collections never contain foreign rows. Unsupported routes have no handler (404/405). ApiError is exactly `{code,messageKey,fieldErrors,correlationId}` with stable translation keys and no submitted secret values. Authentication and personal responses use Cache-Control: no-store.

Public summaries and details expose offering/category/shop content, shop postal address, CHF price, images and summed availability over slots with `startAt > Clock.instant()`. They never serialize slot IDs/timestamps or booking/customer fields, even when a signed-in actor requests the public endpoint. Exhausted published offerings remain discoverable. Only the authenticated customer slot endpoint exposes selectable future start/end, capacity and availability. Customer cart/history is owner-only. Customer order lines expose original quantities/prices, fulfillment state, slot and redisplayable code; provider booking projections expose only their own lines and customer name/email, never a usable code or another provider's lines. Persistence entities are never serialized directly.

Images are uploaded through the provider-owned image command and referenced by server-issued IDs. Validate image content and safe media types, strip metadata, and generate storage names; never fetch arbitrary URLs or accept filesystem paths. Public image reads require a published association; draft images are readable only by the owning provider. Uploaded bytes remain application data subject to the Swiss-storage boundary.

## Database and transaction boundaries

PostgreSQL enforces unique normalized email, one role per account, one shop per provider, one cart per customer, unique `(cart_id,slot_id)`, positive integer capacities/quantities, `start_at < end_at`, foreign keys and positive `NUMERIC(12,2)` offering prices. Every monetary API value is a two-decimal string with explicit CHF; arithmetic uses decimal values and adds no fees, discounts or additional tax. One offering unit price applies to all its slots. One unit admits one person; attendee names are not collected.

Slots have distinct UUID SKUs. Draft overlap is allowed. Published slot ranges use a provider-wide exclusion constraint on provider ID and `tstzrange(start_at,end_at,'[)')` with `btree_gist`; touching boundaries are valid. Publication requires verified, non-suspended ownership, a Swiss postal address, required offering content/image, one fixed category (`TUTOR_LESSON` or `BEAUTY_WELLNESS`), positive price and positive available future inventory. Explicit bulk slot entry supports two or more nonrecurring rows. Once any units are reserved or purchased, schedule edits fail; capacity cannot fall below reserved plus purchased quantities.

Availability is capacity minus cart reservations minus purchased quantity, including delivered and expired purchases. It is never independently writable. All writers share a lock order: affected provider accounts, offerings and slots in stable UUID order, then customer carts/cart lines in stable UUID order; checkout additionally serializes the customer's idempotency key. Price edits acquire the offering lock. Suspension acquires the provider lock before touching listings/carts. Unpublication, reservation release and slot edits follow the same order and recheck state after locking. This prevents reservation-versus-suspension/unpublication races and over-capacity writes. Simple CHECK constraints do not protect cross-row sums: every allocation change must hold the slot lock and recheck the sum.

Quantity changes lock the relevant slot and cart line and apply only the delta in one transaction. Quantity zero means explicit removal. Waiting, sign-out, session expiry, another device, or payment failure has no effect on reservations. Started/expired cart rows remain until an accepted explicit removal trigger; do not introduce a cleanup timer.

Checkout locks all selected cart rows and their slots using the common order. Require nonempty distinct owned selection, active published inventory, verified customer and `now < startAt` for every selected slot. There is no subset success. Recompute current prices under lock; a stale accepted total returns 409 `PRICE_ACCEPTANCE_REQUIRED` before payment, leaves the cart untouched and requires the client to refresh the cart and explicitly accept a fresh total. No implicit retry acceptance occurs.

For an accepted attempt, snapshot line unit prices, quantities and `NUMERIC(12,2)` total before the deterministic simulated payment call. The snapshot cannot change during that attempt; later price edits affect future attempts and carts only. Uniqueness on `(customer_id,idempotency_key)` serializes retries and binds the key to the request fingerprint and terminal result. Replay is checked before cart selection validation, so a successful replay still returns the same order after selected cart rows have gone. A different payload with a used key returns 409 `IDEMPOTENCY_KEY_REUSED`; a failed attempt replays the same failure and a new attempt uses a new key. No key is consumed for pre-payment validation/price rejection.

The synchronous simulated adapter has no external monetary side effects and runs within the bounded attempt transaction. Failure commits only the failed attempt/result, creates no order/booking and retains every reservation. Success commits exactly one marketplace order, all selected booking lines and immutable purchased-price snapshots, then removes selected cart rows by transferring their allocation to purchased units without restoring availability. Unselected rows remain. Emit confirmation and provider-purchase events after commit only. No distributed transaction or live payment guarantee is claimed.

Fulfillment and expiry acquire the marketplace order lock before booking-line locks, consistently in UUID order, so simultaneous lines cannot produce a stale aggregate. Provider redemption authorizes the booking owner before code comparison. With locks held, check Clock again: at or after end, resolve an unresolved line as Expired and reject redemption even if the scheduler has not yet visited it. A scheduled expiry sweep uses the same service/locks and `endAt <= now`; it does not touch carts. Post-commit notifications describe only committed transitions. After successful checkout, due-line processing uses these same rules if the injected time has reached an end boundary. No alternative aggregate or partial-purchase workflow is introduced.

## Exact state transitions and codes

| Aggregate | Allowed transition and effect |
| --- | --- |
| Offering | DRAFT to PUBLISHED after publication validation; PUBLISHED to DRAFT on owner unpublication, atomically releasing all affected cart rows. Purchased lines remain valid and redeemable under existing expiry rules. |
| Provider | Active to suspended by administrator; block sign-in/existing sessions, remove listings from discovery and affected cart reservations, preserve purchased bookings. No reinstatement or fulfillment-access exception is defined. |
| Cart | Add/update/remove reserved quantity; explicit removal, unpublication, suspension or administrator release restores that reservation's inventory. Successful selected checkout transfers allocation. No automatic expiry. |
| Attempt/order creation | Simulated failure produces no order. Simulated success creates one instant-confirmed order and booking lines in AWAITING_FULFILLMENT. |
| Booking line | AWAITING_FULFILLMENT to DELIVERED on valid owner-provider code, for all covered units together, including before start; or to EXPIRED at scheduled end if unredeemed. DELIVERED never expires. Wrong/reused/expired codes never deliver. |
| Administrator override | EXPIRED to DELIVERED only, through the distinct administrator action, without code validation or reactivation. No other override is supported. |
| Marketplace order | AWAITING_FULFILLMENT while any line is unresolved; COMPLETED iff every line is DELIVERED or EXPIRED, including mixed/all-expired orders. Recompute after each transition. No failed or partially completed aggregate. |

Inject UTC `java.time.Clock` everywhere; use offset-bearing RFC 3339 instants at the HTTP boundary. Production-like profiles use the system UTC clock. Only the `e2e` profile registers clock read/advance routes, on loopback/test network with `X-Test-Control` checked against an environment secret. Normal/local/release profiles do not register those routes. Advance is nonnegative and runs due-line expiry before returning; no production clock mutation exists.

Derive each booking line's code with HMAC-SHA-256 using an environment-only secret and an unambiguous, versioned encoding of bookingLineId, orderId, slotId and nonce. Select the lowest nonce whose unbiased four-digit projection is unused by a different slot in that order; use rejection sampling into 0000–9999 rather than biased modulo. Persist the nonce and keyed fingerprint, not the usable code. One purchased slot line covers all its units with one code. Distinct slots within an order have distinct codes; codes may repeat across orders because redemption always selects a booking ID. The four-digit space bounds one order to 10,000 distinct slot lines; reject a larger selection with 422 before payment. Re-derive only for the owning customer's display and simulated confirmation test boundary; compare provider input in constant time after authorization. Never expose codes to provider list/detail responses or logs. Ordinary redemption remains unusable after delivery/expiry/override. No every-attempt history or temporary per-booking block is added.

## Search, language and deferred scope

Search normalized offering name/description, category name/description and shop name using lower-case/unaccent and PostgreSQL trigram similarity for typo tolerance. Rank exact/containment matches ahead of fuzzy matches with a stable ID tie-breaker; quoted phrases use contiguous normalized matching without fuzzy predicates. No grammatical stemmer is used. Empty q returns published services including exhausted ones. Pagination is zero-based with fixed page size 20; filters are category and positive CHF min/max price only; sort is relevance, price_asc or price_desc. Future inventory uses strictly future starts. No date/location filters, public shop page, personalization, saved search or SEO contract is introduced.

Text fields independently contain a submitted-language marker and at least one English/German value, with both optional as a pair. Bilingual content is not mandatory. The UI shows language labels and permits explicit manual-version selection; it does not automatically translate or choose a content version from UI language. UI language follows a supported browser preference, falls back to English, and is switched/persisted only on the device. The planned browser acceptance scope is Chromium at 390px and 1280px, with labels, keyboard access and field errors; this is not an accessibility certification.

The plan supplies minimal implementation details for formerly unanswered cutoff, draft overlap, page size, retry acceptance and fixed-category provisioning. These choices do not reinterpret unanswered owner questions as Yes. Other presentation limits and search tuning stay minimal. Broader suspended-provider fulfillment access remains unimplemented because its exception details are deferred: purchased records remain valid, but suspension creates no provider-access bypass. Other overrides, started-cart cleanup, irreversible deletion, complex publication edits and live payment/expiry exception workflows are not introduced. Retention/legal/tax/backup-region review and hosted operations remain prerequisites in the [storage boundary](../privacy/swiss-storage-boundary.md).

## Threat boundaries and residual risks

| Boundary / asset / abuse | Required control and remaining limitation |
| --- | --- |
| Browser to API; credentials and sessions; CSRF/session theft | Same-origin, CSRF, HttpOnly/SameSite cookies, secure non-local transport, BCrypt, digest-only one-use tokens, session rotation, no-store sensitive responses, safe headers and no secret logging. Real-user security review remains required. |
| Role/owner boundary; bookings and customer details; cross-owner access | Derive Actor from the session, enforce role/owner in service queries and projections, authorize before code comparison, keep administrator override separate. No provider access bypass for suspension. |
| API to database; inventory, prices and orders; overselling/replay | Exclusion/uniqueness/check constraints, common row-lock order, atomic allocation transfer, accepted snapshots and request-bound idempotency. Manual reservation release addresses abandoned-cart hoarding; there is no timer or stronger anti-hoarding product feature. |
| Fulfillment; four-digit secrets; guessing/reuse | Booking-selected owner authorization, HMAC derivation, constant-time comparison, single terminal transition under locks, end-time check. Four digits provide limited guessing resistance; no temporary booking-level block or every-attempt audit-history feature is claimed. Early redemption is allowed and does not prove physical delivery. |
| Administrator to domain; misuse | Explicit ADMINISTRATOR role and exactly three mutations with state preconditions; no code reactivation, general override or destructive record removal. Production administrative safeguards remain deferred. |
| API to simulated ports; secrets/notifications | Deterministic replaceable adapters, test spies only, post-commit notifications and redacted logs. No real email/payment delivery, inbox, card data or durable external delivery guarantee. |
| Image bytes and e2e control to API | Safe decoded images/server IDs; no arbitrary URL fetch or client storage path. Test clock exists only in e2e with network/header isolation; release route absence must be tested. |
| Local tracking to GitHub; false approval or sensitive evidence | Local Studio remains authoritative, redact outbound evidence, remote progress creates no approval. This is a design boundary, not a tracking/lifecycle operation. |
| Untrusted PR to CI and validated source to artifacts | Least-privilege PR checks without publication credentials; pinned inputs; release artifacts only from successful exact-main-revision validation, carrying source/checksums/toolchain/evidence identity. Produce reproducible archives/container-image artifacts only; registry publication and environment deployment remain excluded. |

Contract impact: Tasks 4, 6, 8 and 10 implement these operations and invariants; their client consumers use the same records and errors. Behavioral deviations return to the Orchestrator. This snapshot introduces no cancellation, rescheduling, refunds, messaging, account deletion, data-export UI, analytics, category editing, direct service hiding, organizations/staff, remote/home delivery, recurring schedules or ownership transfer.
